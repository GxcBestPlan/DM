## 1. 项目背景

公司开发组织划分为**多个开发小队**（每队 10-15 人，纯 Web 前后端开发 + 测试），每个小队**独立运行两周一个版本**的迭代节奏。目前需求池、排期、每日进度全部依赖**线下 Excel** 管理，存在协作效率低、信息不同步的问题。

本系统将该流程线上化，服务产品经理、开发管理者、开发人员、测试人员四类角色，以及需要跨队统筹的管理者。

## 2. 目标与角色价值

### 2.1 总体目标

1. **进度实时透明**：任何人可随时看到需求/任务的最新状态，无需逐个询问；
2. **排期有据可依**：排入管道时可见人员负载，冲突/超载有系统提示；
3. **历史可沉淀**：状态流转全程留痕，版本结束可复盘、可统计。

### 2.2 各角色价值

| 角色 | 获得的价值 |
|---|---|
| 产品经理 | 需求池统一录入管理、拖拽定序、随时查看需求生命周期 |
| 开发管理者 | 排期时看到人员×日期负载，冲突预警；进度无需追问；版本统计自动生成 |
| 开发人员 | 每天打开即知自己今日任务；一键更新状态，无需口头汇报 |
| 测试人员 | 清晰的待测试队列，不再挤在版本末尾或被晾着 |
| 跨队管理者 | 全局视图：各小队迭代进度、负载总览、延期风险 |

## 3. 术语表

| 术语 | 含义 |
|---|---|
| 需求（Requirement） | 一次要交付的业务变更/缺陷修复/优化/技术债，最小排期单元 |
| 需求池 | 本队尚未排入迭代的需求集合，按产品经理定的顺序排列 |
| 迭代（Sprint） | 一个小队一个两周的开发周期，独立排期与交付 |
| 任务（Task） | 需求拆解后的开发工作单元（前端任务/后端任务） |
| 插队 | 迭代进行中紧急需求的临时插入 |
| 阻塞（Blocked） | 需求/任务因外部原因暂停，需记录原因 |

## 4. 范围

### 4.1 本期范围（MVP）

- 需求池管理（录入、编辑、定序、评审状态）
- 迭代管理（创建、排期、关闭）
- 任务拆解与依赖（前端/后端任务、依赖关系）
- 管道排期视图（人员×日期负载、冲突检测）
- 每日推进（任务状态更新、进展备注）
- 测试与验收流转
- 插队处理
- 跨队管理者总览视图
- 统计报表（进展、完成情况）
- 账号登录与角色权限

### 4.2 不在本期范围

- 与外部系统（Jira/禅道/IM）对接
- Excel/历史数据批量导入（上线后人工前台录入补充）
- 移动端 App（浏览器桌面端优先，后续可考虑）
- 代码仓库/CI 集成
- 工时精细化到小时的填报

## 5. 组织与角色模型

### 5.1 组织结构

```
组织（全局）
├── 全局角色：系统管理员(admin) / 跨队管理者(supervisor)
└── 多个小队 Team（每队 10-15 人）
    ├── 产品经理 pm（每队至少 1 人，可能多人）
    ├── 开发管理者 dev_manager（每队 1 人）
    ├── 前端开发 frontend_dev（若干）
    ├── 后端开发 backend_dev（若干）
    └── 测试 tester（若干）
```

### 5.2 角色职责

| 角色 | 主要职责 | 系统内行为 |
|---|---|---|
| 产品经理 | 维护本队需求池 | 录入需求、评审前后修改、拖拽定序、预估人日 |
| 开发管理者 | 版本排期与调度 | 选需求入迭代、拆任务、分配人员、处理插队、关闭迭代、看统计 |
| 开发人员 | 按任务开发 | 认领/查看任务、更新状态与进展备注、登记阻塞 |
| 测试人员 | 验收 | 处理"待测试"需求、通过/退回 |
| 跨队管理者 | 统筹 | 查看所有小队迭代进度、负载、延期风险（详见 5.4 权限假设） |
| 系统管理员 | 组织维护 | 小队/成员/角色管理 |

> 一个用户属于**一个小队**，可在队内担任**多个角色**（如同时是后端开发）。

### 5.3 权限矩阵（草案）

| 功能域 | 本队 PM | 本队开发管理者 | 本队开发/测试 | 跨队管理者 | 系统管理员 |
|---|:---:|:---:|:---:|:---:|:---:|
| 看本队需求池 | ✅ | ✅ | 只读 | 只读 | ✅ |
| 需求录入/定序 | ✅ | — | — | — | — |
| 需求排入迭代/拆任务/分配 | — | ✅ | — | — | — |
| 本队迭代看板 | ✅ | ✅ | ✅ | ✅(全部队) | ✅ |
| 管道排期视图 | 只读 | ✅ | 只读 | ✅(全部队) | ✅ |
| 任务状态更新 | — | ✅ | 本人任务✅ | — | — |
| 测试通过/退回 | — | — | tester✅ | — | — |
| 统计报表 | 本队 | 本队 | 只读 | 全部队 | ✅ |
| 成员/角色管理 | — | 建议✅ | — | — | ✅ |

> ✅ **已确认（v1.0）**：跨队管理者为**只读总览 + 全部队报表**，不直接操作其他队的排期（见 §14 决策 1）。

## 6. 核心对象

| 对象 | 关键字段 |
|---|---|
| 用户 | 账号、密码(加密)、姓名、全局角色 |
| 小队 | 名称、描述 |
| 成员 | 小队、用户、角色（可多角色） |
| 迭代 | 小队、名称、起止日期、状态 |
| 需求 | 小队、所属迭代(空=在池)、标题、描述、类型、状态、池内排序、预估(人日)、插队标记、阻塞标记与原因、验收标准、外部依赖备注(选填)、创建人 |

## 7. 状态机

### 7.1 需求状态

**池内阶段**（尚未排入迭代）：

```
待评审 ──评审通过──▶ 已评审（可排期）
   ▲                    │
   │   评审退回(带意见)   ▼（评审意见修改后可再评审）
   └──────── 待评审 ◀───┘
```

**迭代内阶段**（已排入某迭代）：

```
已排期（未开工）→ 开发中 → 待测试 → 测试中 → 已验收 → 已发布
                    ▲                    │
                    └────验收不通过(退回)─┘
```

- 测试不通过退回后回到**开发中**，修复后重新走测试
- 全部开发任务完成后，需求由开发管理者或系统规则转 **待测试**（v1.0 起不再设"联调中"环节）
- 任意状态可挂 **阻塞**（原因必填），解除后回到原状态
- 另设 **已取消**（需求被放弃，保留记录用于统计）

### 7.2 任务状态

```
待开始 → 进行中 → 已完成
```

- 任务可挂阻塞（原因必填）
- 任务完成后前端/后端各自就绪，需求状态由开发管理者或系统规则推进（全部开发任务完成 → 进入待测试）

### 7.3 迭代状态

```
规划中(planned) → 进行中(active) → 已关闭(closed)
```

- 迭代创建时处于规划中，可调整需求；开始后进入进行中
- 关闭后需求/任务只读，数据沉淀用于统计

### 7.4 插队与变更

- 迭代进行中，开发管理者可将池内需求**插队**入当前迭代（带 urgent 标记）
- 插队时系统展示影响提示：当前相关人员负载情况，供管理者决策（是否顺延其他需求）

## 8. 核心业务流程

### 8.1 需求池管理（产品经理）

1. PM 录入需求（标题/描述/类型/预估人日/验收标准）
2. 需求进入本队池，状态"待评审"
3. 评审在线下进行，系统仅登记结论：通过 → "已评审"（须已填写验收标准，v1.0 起必填）；退回 → 附意见（必填），PM 修改后再提
4. PM 对"已评审"需求**拖拽定序**（决定排期优先取用顺序）

### 8.2 迭代排期（开发管理者）

1. 迭代开始前，从池内按序挑选需求排入迭代（支持一次多选）
2. 为需求拆任务：前端任务 / 后端任务（测试不拆任务，在需求级进行）
3. 标注任务依赖（如前端任务依赖某后端任务）
4. 分配任务给具体开发人员
5. 系统实时检测：**同一人员同日任务冲突/总负载超限** → 高亮预警；依赖未满足 → 提示
6. 迭代开启后进入进行中

### 8.3 开发推进

1. 开发人员看到"我的任务"，开始 → 进行中
2. 每天或节点更新：状态 + 进展备注（可选，一句话说明今天进展/卡点）
3. 任务依赖仅作**顺序提示**：所依赖的后端任务未完成时，前端任务标记"已完成"会给出提示，不阻断（v1.0 起不设"联调中"环节）
4. 全部开发任务完成 → 需求转"待测试"

### 8.4 测试与验收

1. 测试人员从"待测试"队列领取需求 → "测试中"
2. 通过 → "已验收"；发布由开发管理者**手动标记**为"已发布"（本期无发布系统对接，仅已验收需求可标记）；不通过 → 退回开发（"验收不通过"，附原因）
3. 系统使测试队列对管理者可见：**版本末期待测试堆积预警**

### 8.5 迭代结束与复盘

1. 开发管理者关闭迭代 → 需求/任务只读
2. 自动生成迭代报告：需求完成率、按期完成率、状态分布、按天完成趋势、人均负载
3. 历史迭代数据可随时回看（状态日志支撑）

## 9. 功能需求（页面级）

### 9.1 登录与个人中心
- 账号密码登录（JWT），登录后按角色呈现工作台
- 展示本人小队、角色、今日任务概览

### 9.2 跨队总览页（supervisor / admin）
- 各小队：当前迭代名称/剩余天数、需求总数与完成数、延期高风险需求数
- 各小队人力负载总览（超载小队高亮）
- 可下钻查看任意小队迭代看板/管道视图（只读）

### 9.3 需求池页（PM 为主）
- 列表展示：排序（拖拽）、类型筛选、状态筛选、创建人筛选、关键字搜索
- 录入/编辑需求（验收标准在登记"评审通过"前必填）、登记评审结果、预估人日
- 已评审需求可被"排入当前迭代"操作（或由开发管理者操作）

### 9.4 迭代管理页（开发管理者）
- 迭代列表：当前迭代（名称、起止、剩余天数、状态、排期需求数与完成数）与历史迭代（完成率、报告入口）
- 创建迭代（名称、起止日期）、开始迭代（规划中→进行中）、关闭迭代（→已关闭，需求/任务只读）、重新打开
- 排入 / 移出需求：列出本队"已评审"需求，选中排入当前迭代；已排期需求可移回需求池
- 插队：将池内已评审需求插入进行中的迭代，展示受影响人员/任务重叠提示，由管理者决定是否顺延（不自动顺延）

### 9.5 迭代看板页（全员）
- 当前迭代需求按状态分列（开发中/待测试/测试中/已验收…），任务以卡片内嵌于需求下
- 点开需求查看详情：描述、验收标准、任务列表与依赖、状态历史（时间线）
- 支持按人筛选（看某人的任务）

### 9.6 管道排期视图（开发管理者核心页）
- 表格/甘特：**人员 × 日期**（两周），格内为任务
- 同一人同日多任务、周负载超限 → **冲突高亮**
- 拖拽任务调整日期/人员，实时重算冲突
- 插队需求排入时显示影响提示

### 9.7 我的任务页（开发人员）
- 今日待办（进行中 + 今日应开始）、我的全部任务（按迭代）
- 操作：开始/完成、改状态、写进展备注、挂/解阻塞

### 9.8 测试工作台（测试人员）
- 待测试队列（按迭代/小队）、测试中、我验收的历史
- 操作：领取 → 测试中 → 通过(已验收)/退回(验收不通过 + 原因)

### 9.9 统计报表页（管理者）
- 迭代报告：完成率（完成需求/排期需求）、状态分布图、按天完成趋势（燃尽）
- 按期完成率（按排期承诺对比实际完成时间）
- 跨队汇总（supervisor）：各队版本完成率对比、延期需求 Top 列表

### 9.10 组织管理页（admin）
- 小队增删改；成员添加/移除；成员角色配置（可多角色）
- 账号启用/停用、重置密码

## 10. 关键业务规则

1. 池内排序由 PM 拖拽产生，同队内唯一有序
2. 需求只能属于**一个迭代**（或停留在池）
3. 需求预估人日**必填**，按 **0.5 天粒度**、取值 ≥ 0.5（排期计算依据）
4. 任务必须属于一个已排期（进行中迭代）的需求
5. 任务依赖（仅前后端任务之间，禁止循环依赖，系统校验）只作**顺序提示**：被依赖任务未完成时，依赖任务标记完成给出提示，不阻断状态流转
6. 插队（urgent）需求排入后，系统给出受影响人员/需求提示，**不强制**顺延，由开发管理者决定
7. 阻塞必须有原因，解除需记录；阻塞时长计入迭代报告
8. 状态变化必须写状态日志（谁、何时、从哪到哪）
9. 迭代关闭后不可再变更（只读），需变更走"重新打开"权限操作
10. 测试退回必须填原因；被退回需求回到开发中，其开发任务按需重新指派

## 11. 统计与报表需求（本期）

| 报表 | 指标 |
|---|---|
| 迭代进展 | 各状态需求数量分布、按天完成需求数趋势、剩余预估人日 |
| 迭代完成 | 完成率、按期完成率、插队需求数及占比、阻塞时长汇总 |
| 跨队总览 | 各队当前迭代完成率、超载/延期风险标记 |
| 个人负载 | 迭代内每人承担任务数/预估人日合计（管道视图直接体现） |

## 12. 非功能需求

1. **登录认证**：全员账号 + JWT；密码加密存储；登录态失效策略
2. **权限控制**：按 5.3 权限矩阵在前端隐藏 + 后端强制校验
3. **部署**：公司内网 Web 部署；后端 Spring Boot(8080) + 前端 Vite/Vue3（构建后静态部署或同端口代理），MySQL 存储
4. **规模预估**：数十账号；每队每迭代数十需求；单机部署即可，接口响应 < 1s
5. **浏览器**：Chrome/Edge 桌面端优先；页面布局适配 1366px 以上
6. **数据**：需求/任务/日志长期保留，无自动清理
7. **易用性**：状态更新 ≤2 步完成（开发人员高频操作，追求极简）

## 13. 数据与迁移

- 上线时不做历史数据批量导入
- 进行中工作由各角色**登录后人工录入补齐**（先建组织/小队/成员，再补需求池与当前迭代）
